# J'Donuts

A Flutter customer app for J'Donuts: onboarding with registration and log-in,
an offline-first Home and Product detail, and an animated Rewards screen.

| | |
|---|---|
| Flutter | 3.47.5 (stable) |
| Dart | 3.12.2 |
| Android | release APK builds with `flutter build apk --release` |
| iOS | builds on macOS only (see [Known gaps](#known-gaps)) |

## Running it

```sh
flutter pub get
flutter run
```

The app needs no server. It seeds its database from the bundled
`assets/seed/*.json` on first launch and works fully offline from then on.

**Fake OTP code: `123456`.** Any other code is rejected, three wrong codes
lock the screen until a new code is requested, and the code "expires" after
5:00.

### The mock server (optional)

The app refreshes the public catalogue (products, banners, sections, shops)
from a small mock API when it can reach one:

```sh
cd mock_server
dart pub get
dart run bin/server.dart              # http://localhost:8080/v1
dart run bin/server.dart --promo      # changed catalogue, to watch a refresh land
dart run bin/server.dart --latency 2000
```

Every response uses the `{data, error, meta}` envelope. Routes:
`/v1/health`, `/v1/products`, `/v1/banners`, `/v1/sections`, `/v1/shops`,
`/v1/images/<file>`. The server reads the same `assets/seed/catalog.json` the
app seeds from, so the two cannot disagree.

By default the Android emulator reaches it on `10.0.2.2:8080` and the iOS
simulator on `localhost:8080`. For a physical phone:

```sh
flutter run --dart-define=API_BASE_URL=http://<your-computer's-LAN-IP>:8080
```

### Tests and checks

```sh
flutter analyze                 # no issues
flutter test                    # 97 tests: unit, bloc, widget, app flow, layout
flutter test integration_test   # needs a device or emulator
```

- **Unit:** validators (phone, OTP, name, date of birth), use cases, the
  fake auth repository, repositories against an in-memory Drift database,
  the seed import, and the router's auth guard.
- **Widget:** login and registration validation, including the OTP screen.
- **App flow:** the real app with in-memory storage. Register → Welcome →
  Home → Product detail → Add to cart; log out and log back in; Rewards
  reading the same member record as Home.
- **Layout:** every main screen on a 4.7" (360 × 640) and a 6.9"
  (440 × 956) phone at text scale 1.3. Any overflow fails the test.
- **Integration:** `integration_test/app_test.dart` runs Register → Welcome
  → Home → Product detail on a device, reusing the app-flow helpers.

**CI** (`.github/workflows/ci.yml`) runs the analyzer and the tests, builds
the release APK and an iOS simulator app (both uploaded as artifacts), and
runs the integration test on an Android emulator.

The drawn images in `assets/images/` are generated by code; regenerate them
with `flutter test tool/generate_art_test.dart`. Drift code is generated with
`dart run build_runner build`.

## Architecture

Clean architecture, organised by feature. Each feature has `domain` (entities,
repository interfaces, use cases; no Flutter imports), `data` (Drift and Dio
sources, mappers, repository implementations), `presentation` (cubits,
pages, widgets) and `di` (its get_it registrations).

```
lib/
  app/
    bootstrap/    startup: DI, seed import, session restore, background sync
    di/           get_it wiring; CoreModule takes test overrides
    router/       go_router, auth redirect guard, page transitions
    shell/        bottom navigation with the sliding pill
    sync/         background catalogue refresh on start and on reconnect
  core/
    database/     Drift schema with versioned migrations
    connectivity/ connectivity_plus plus a DNS reachability probe
    images/       AppImage: network via disk cache, bundled asset as fallback
    motion/       every duration and curve (app_motion.dart)
    widgets/      shared widgets: buttons, skeletons, banners, sheets
  features/
    auth/         onboarding, phone, OTP, name, date of birth, welcome, log-in
    home/         member header, banners, product sections, shops
    product/      product detail, quantity stepper, cart
    member/       the one member record Home and Rewards both read
    rewards/      points ring, tier ladder, tabs, challenge cards
    settings/     log out
  l10n/           ARB files (English, Burmese) and gen-l10n output
packages/
  app_core/       Result<T>, typed failures, use-case contracts (pure Dart)
  app_network/    Dio factory: timeouts, retry with backoff, logging, envelope
  app_storage/    secure storage interface and implementations
  app_ui_kit/     design tokens (palette, spacing, radii, type) and the theme
mock_server/      shelf mock API
tool/             the image generator
```

**Routing.** go_router with a pure `authRedirect` guard, re-evaluated
whenever the session changes. Signed-out users can only reach onboarding,
register and log-in. A finished registration lands on Welcome, and a
signed-in user never sees onboarding. Registration and log-in steps share a
shell, so the back button and progress ring stay put while the steps slide,
and going back keeps what was typed. The tabs use
`StatefulShellRoute.indexedStack`; Product detail is `/product/:id`.

**Errors.** Repositories return `Result<T>` with typed failures
(`NetworkFailure`, `ServerFailure`, `CacheFailure`, `NotFoundFailure`, …)
instead of throwing. Each Home and Rewards section has its own loading,
empty and error state, so one broken section never blanks the others.

**Networking.** Dio with 5 s connect and 10 s receive timeouts, up to two
retries with backoff for GET and HEAD requests that failed on the network,
and request logging in debug builds.

### State management: BLoC (Cubit)

I chose Cubits with get_it because the screens are driven by database
streams. A cubit subscribes, maps rows into an immutable state and closes
its subscriptions, which keeps that flow explicit and easy to test with
`bloc_test`. Cubits are created per route by `BlocProvider`, so a screen's
state lives exactly as long as the screen. The session is the one app-wide
cubit, and the router listens to it.

## Offline strategy

- **The database is the single source of truth.** Screens only read Drift
  `watch()` streams; nothing reads the network directly.
- **First launch** imports the bundled seed into the database (the seed is
  versioned), so the very first open works in airplane mode.
- **Refresh** runs in the background at start-up and whenever connectivity
  comes back, and on demand with pull-to-refresh on Home. New data lands in
  the database and open screens update through their streams. A failed
  refresh leaves the existing data untouched.
- **Online means reachable.** connectivity_plus says whether there is a
  network, and a DNS lookup confirms it reaches the internet. The offline
  banner follows that.
- **Images** come from the disk cache (`cached_network_image` with a
  dedicated cache manager) when the server has them, and from the bundled
  copy otherwise, so every seeded product has a picture offline, even on
  first launch.
- **Private data** (member record, challenges, cart, registered users) is
  local only. The member record is a single row that Home and Rewards both
  watch, so the name entered during registration shows on both.
- **The session** is kept in flutter_secure_storage.

## Animations

All durations and curves live in `lib/core/motion/app_motion.dart`.

| Where | What |
|---|---|
| Onboarding | Donut circles enter one after another, then drift gently |
| Registration | Shared-axis slide between steps; the progress ring sweeps to the next step; the button morphs into a spinner while "sending"; a wrong OTP shakes the code boxes |
| Welcome | Content enters in a stagger |
| Home | Skeleton shimmer while loading; the banner carousel auto-slides; tiles scale on press |
| Product detail | Hero image from the Home tile; quantity and total update as you tap |
| Rewards | The points ring sweeps while the total counts up to 680,000. Tiers appear in order (Silver, Gold, Platinum), then the line fills towards the next tier. The tab pill slides and the list cross-fades. Challenge cards enter staggered while their donut quarters and coffee arc (9/12) fill. The Earn button pulses when a challenge is complete and is grey otherwise. Cards give press feedback. The Rewards badge (3) pops in |
| Bottom navigation | The pink pill slides to the selected tab |

**Reduce Motion.** When the system asks for less motion, every duration
collapses to 1 ms, looping animations stop and the carousel stops
auto-sliding. Everything still reaches its final state.

## Localisation and layout

Strings live in ARB files and are generated with gen-l10n. English is
complete; Burmese is the bonus language and follows the device language.
Text scales up to 1.3, and the layouts hold from 4.7" to 6.9" phones, which
the layout test checks.

## Known gaps

- **iOS was not built or run.** Development was on Windows, which cannot
  build iOS. The iOS project is configured (display name, local-network ATS
  exception for the mock server, localisations), and the CI workflow builds
  a simulator app on a macOS runner, but that workflow has not run yet.
- **The integration test has not run on a device yet.** No emulator was
  available on the development machine; the CI workflow runs it on an
  Android emulator. The same flow passes as a widget test against the real
  app (`test/app/app_flow_test.dart`).
- **Placeholders, as the brief allows:** social sign-in, Terms of Use,
  Privacy Policy and the section "see all" buttons open a "coming soon"
  sheet; the Menu and Wallet tabs are placeholder pages.
- **Cart** keeps quantities and the total in the database. There is no
  checkout screen.
- **Artwork.** The client's designs may not be published, so every image is
  original art drawn in code. It follows the designs' layout and colours,
  not their photography.
- **Burmese copy** should be reviewed by a native speaker before release.
- **Design screenshots are not in this repository** and must not be added:
  they belong to the client.
